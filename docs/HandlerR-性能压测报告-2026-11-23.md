# HandlerR 1.0.0 性能压测报告

测试日期为 2026 年 11 月 23 日。测试使用从本地 NuGet 源安装的 `HandlerR 1.0.0` 和 `HandlerR.Contracts 1.0.0`，运行时代码对应提交 `cc595c0`。 [代码提交](https://github.com/sugarst/HandlerR/commit/cc595c06a6637fc6d0df9a3399f23e5978850329)

在 4 CPU 配额下，两种注册模式都在 **4 个工作线程**时达到本轮闭环峰值。反射注册为 **352.2 万次/秒**，源生成注册为 **330.1 万次/秒**。提升到 64 个工作线程后，两者吞吐均下降，尾延迟升高。

源生成模式以 **231.09 万次/秒**固定到达速率持续运行 **5 分钟**，完成 **693,270,000 次操作**，零错误、零漏处理。**从计划到达至完成的 P95 为 42.21 ms，P99 为 121.11 ms**。同期从工作线程开始处理算起的 P95/P99 为 **2.143/3.343 µs**。评估这轮高负载的响应时间时，应使用包含调度和排队的端到端数据。

## 测试环境与工作负载

| 项目 | 配置 |
| --- | --- |
| 运行环境 | Docker 容器，Ubuntu 24.04.5 LTS，Linux x86_64 |
| 硬件与限额 | Intel Core i7-14700，容器限额 4 CPU、2 GiB 内存 |
| .NET | SDK `10.0.404`，运行时 `10.0.15`，Release，Server GC |
| 注册方式 | `AddHandlerR` 反射注册、`AddGeneratedHandlerR` 源生成注册，两种模式均运行在 JIT 宿主 |
| 调用方式 | 每次顶层操作创建独立 DI 作用域，从中解析 `IDispatcher` |
| 请求行为 | 注册 `TelemetryBehavior` 和 `ValidationBehavior`。订单命令校验数量，压测进程未配置遥测导出器 |

每个查询、订单或流式请求记为一次顶层操作。订单的两路通知和流式请求的 20 个元素计入对应顶层操作的耗时。

| 流量占比 | 场景 | 执行内容 |
| ---: | --- | --- |
| 60% | 商品查询 | 从内存目录读取价格，并校验返回值 |
| 25% | 订单处理 | 校验数量、原子预留库存，再顺序发布通知，由库存和审计处理器分别接收 |
| 15% | 流式查询 | 完整消费 20 个元素，并核对返回条数与值的总和 |

### 测量口径

- **闭环阶梯**以 1、4、16、64 个工作线程运行。每种注册模式用 4 个线程预热 5 秒，再在各并发档位观测 12 秒。每个工作线程完成当前操作后立即发起下一次。
- **定速持续负载**使用 8 个工作线程和源生成注册。将其 4 线程闭环吞吐的 70% 向下取整到百位，得到每秒 2,310,900 次的计划到达速率。先用同一速率试跑 10 秒，再正式测量 300 秒。
- **执行延迟**从工作线程开始处理算到操作完成，包含 DI 作用域和业务处理。**端到端延迟**从预先排定的到达时间算起，还包含发压调度和工作线程积压带来的等待。
- 百分位来自全部成功操作的直方图，使用对应分桶的上界。闭环吞吐按实际运行时长计算。定速吞吐按 300 秒内完成的成功操作数计算，窗口结束后的完成数另记。

| 指标 | 实测 |
| --- | ---: |
| 计划到达速率 | 2,310,900 次/秒 |
| 300 秒窗口内完成吞吐 | 2,310,896.7 次/秒 |
| 计划到达 / 最终完成 | 693,270,000 / 693,270,000 |
| 窗口结束后完成 | 986 次，约 1.2 ms 内排空 |
| 执行错误 / 未完成 | 0 / 0 |
| 完成订单 | 173,317,486 笔 |
| 库存通知 / 审计通知 | 173,317,486 / 173,317,486 |
| 进程 RSS，开始 → 结束 | 100.18 → 105.28 MiB |
| GC 次数，Gen 0 / 1 / 2 | 71,691 / 0 / 0 |
| 进程 CPU 时间 | 1,197.92 CPU 秒，约合持续使用 3.99 个 CPU |

CPU 时间覆盖发压、统计和 HandlerR 业务执行。RSS 是进程常驻内存的采样值。

| 计时口径 | P50 | P95 | P99 | P99.9 | 最大值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 执行延迟（µs） | 0.879 | 2.143 | 3.343 | 31.871 | 100,147.257 |
| 端到端延迟（ms） | 14.22 | 42.21 | 121.11 | 325.06 | 418.84 |

按**计划到达时刻**划分每分钟的样本。每组均有 138,654,000 次操作，表中延迟包含跨分钟完成的操作。

| 计划到达窗口 | 端到端 P95（ms） | 端到端 P99（ms） | 窗口末 RSS 采样（MiB） |
| --- | ---: | ---: | ---: |
| 第 1 分钟 | 40.89 | 46.66 | 104.06 |
| 第 2 分钟 | 121.11 | 299.89 | 105.10 |
| 第 3 分钟 | 41.16 | 49.28 | 104.76 |
| 第 4 分钟 | 41.16 | 49.81 | 105.14 |
| 第 5 分钟 | 40.63 | 45.88 | 105.28 |

第 2 分钟的端到端 P99 达到 299.89 ms，随后三个窗口回到 45.88–49.81 ms。高负载尾延迟应同时看整轮百分位和分窗口数据，整轮均值会掩盖这种短时波动。

## 结果适用范围

- 吞吐和延迟对应这台机器、容器配额和内存业务负载。带 HTTP、数据库或实际遥测导出的服务需要按完整业务路径测量。
- 两种注册方式的闭环测试在同一进程中先后运行，每档测量一次。表中的差异用于描述这次实测，判断注册模式间的稳定性能差异需要独立重复测量。
- 持续阶段覆盖一个定速负载点和 5 分钟内存观测。数据可用于说明该负载下释放积压和完成通知的情况，小时级稳定性与生产延迟目标应按对应要求另行验证。

## 原始数据与复现

以下文件保存在运行压测的机器上，路径相对于仓库根目录为 `artifacts/handler-load-20261123-160922/`。该目录在 Git 忽略范围内。

- `results.jsonl` 记录各档位的指标与定速测试的分分钟结果。
- `environment.log` 记录环境、包 SHA-256 和构建日志。
- `Program.cs`、`HandlerR.Load.csproj`、`NuGet.Config` 和 `feed/` 用于复现。

复现时，将压测项目、`global.json`、`NuGet.Config` 和 `feed/` 放入隔离的 Ubuntu x64 容器目录。使用同一包和资源限额，执行以下命令。

```bash
dotnet restore HandlerR.Load.csproj --configfile NuGet.Config
dotnet build HandlerR.Load.csproj -c Release --no-restore
dotnet bin/Release/net10.0/HandlerR.Load.dll | tee results.jsonl
```
